# Testing and benchmarks

## Commands

```sh
cargo build
cargo test                                         # statistical tests run optimised (opt-level 3)
cargo test --release -- --include-ignored          # everything, with the long statistical runs
cargo clippy --all-targets -- -D warnings
cargo docs                                         # API documentation with rendered formulas (KaTeX)
cargo bench                                        # criterion: benches/{sign,keygen,e2e}.rs
python3 tools/gauss_tables.py --check              # src/tables.rs against its definition (mpmath)
```

`cargo test` runs 137 tests: 77 unit tests, 59 integration tests in 15 files, and 1 doctest.
Twelve more are ignored by default because they are long; `cargo test --release --
--include-ignored` runs all 149 in about 82 s on an Apple M4. The `simd` feature adds the
tests that compare its kernels with the portable code: one on aarch64, two on x86-64.

## What the tests cover

- **Parity with fn-dsa** at Falcon-1024's parameters (`tests/parity_fndsa*.rs`):
  - fn-dsa's signing known-answer test is reproduced byte for byte;
  - on 2048 messages (65,536 in an ignored run), fn-dsa's signer replayed around this crate's
    SampPre core gives the same signature and the same `s`, on fn-dsa's keys, on this crate's
    keys and at fn-dsa's toy degrees;
  - fn-dsa verifies preimages made with the public `samp_pre`.

  Output parity certifies every discrete decision and the constants (to about 10^-8 relative),
  not IEEE bit patterns. A unit test adds the bit level: the precomputed tree gives exactly the
  leaf centres and widths of fn-dsa's per-attempt recursion.
- **Known answers** (`tests/kat.rs`): TrapGen and SampPre at both presets.
- **Distribution:**
  - the coset Gaussian, enumerated exactly at toy size;
  - SamplerZ against the exact discrete Gaussian across the leaf widths;
  - the `f, g` sampler against `D_{Z,σ_fg}`;
  - a 200-bit replay of ffSampling;
  - the far-tail trial that fn-dsa's `BerExp` would accept.
- **Key generation** against Sage: NTRUSolve, the Gram–Schmidt norms and the whole candidate loop.
  The NTT check of `fG − gF = q` is tested against a big-integer oracle.
- **End to end and hardening** (`tests/pipeline.rs`, `tests/hardening.rs`):
  - `fG − gF = q` and `h f = g`, the norm bounds, the leaf range, SampPre's equation and norm
    bound, and the encodings, each re-checked by an independent computation;
  - the refusal of inconsistent trapdoors and invalid rings, the leaf windows, and the refusal of
    a Gram–Schmidt bound above `(1.17 √q)²` (security.md, "Key distribution").

The statistical tools in [`examples/`](../examples) and the analysis scripts in
[`tools/stats/`](../tools/stats) reproduce the figures of [precision.md](precision.md), and
`examples/stats_density.rs` and `tools/stats/ntru_fatigue.py` those of the key-distribution
section of [security.md](security.md). The Sage
fixtures are generated by `tools/keygen/fixtures.sage.py` and `tools/sign/precision_fixture.sage.py`,
with the exact NTRUSolve oracle of `tools/ntru_sizes.py`.

Built with `-C target-cpu=x86-64-v3` (AVX2, BMI2), the Xeon computes SampPre in 225 µs and
279 µs, Verify in 32.2 µs and a multiplication in 41.1 µs, with the same outputs. With the `simd`
feature as well, Verify takes 19.4 µs and a multiplication 21.8 µs, while SampPre stays at 225 µs
and 277 µs: the compiler then emits the BMI2 instructions of the Keccak kernel by itself. With
`-C target-cpu=native` (AVX-512), SampPre at `Params::PCS` was slower than with x86-64-v3 in the
measurements that preceded 0.1.2 (320 µs against 264 µs).

At `Params::PCS`, SampPre spends about 99 µs on its 2048 leaf samples (about 48 ns each on the M4)
and the rest on the FFT, the tree and the lattice-point arithmetic. A profile of 0.1.2 attributed
about 52 % of its time to the leaf sampler and 27 % to the SHAKE256 permutation. TrapGen is
dominated by NTRUSolve on resultants of about 9.6 kbit, with 20.2 candidates per key on average.

## Interoperability with fn-dsa

fn-dsa's verifying key stores `h` in its NTT representation, not in coefficient form.
`tests/e2e.rs` (`fndsa_vk`) converts this crate's `h` with fn-dsa-comm's `mqpoly_*` functions.

## Limitations of the testing

- On x86-64 (the Xeon above, Ubuntu 24.04, rustc 1.100.0) the whole suite passes, the long tests
  and the parity tests against fn-dsa included, for the default target. The unit, known-answer
  and parity tests also pass with `-C target-cpu=x86-64-v3` and `-C target-cpu=native`. Other
  x86-64 processors and compilers have not been tested.
- With the `simd` feature the whole suite passes on the Xeon (AVX2, BMI1 and BMI2) and on the M4
  (NEON), and the unit, known-answer and parity tests pass with `NTRU_TRAPDOOR_SCALAR` set and,
  on the Xeon, with `-C target-cpu=x86-64-v3`. The kernel tests compare each kernel with the
  portable code on random values and on 0, 1 and p − 1. An x86-64 processor without AVX2, on
  which the portable code runs, was only imitated, with `NTRU_TRAPDOOR_SCALAR`.
- The MSRV, 1.95, has not been run itself: the code was checked with rustc 1.93.1 and tested with
  1.99.0.
